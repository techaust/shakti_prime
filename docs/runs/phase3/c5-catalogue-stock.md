## Brief
Build [phase3 §6.1](../../03-roadmap-appendix/phase3.md#61-c5-catalogue-for-stock) as written. Points the design leaves to you, settled here:

1. **Columns on `items`:** `warranty_months` and `supplier_warranty_months` (smallint, 0 to 360, null when not set), `barcode` (text, unique where not null, 4 to 64 printable characters), `purchase_unit` (one of the existing unit values, null meaning the stock unit), `purchase_unit_factor` (`numeric(12,3)`, at least 1, required when `purchase_unit` is set and differs from `unit`), `serial_pattern` (text of at most 200 characters, only on a serial-tracked item), `is_stocked` (boolean, default true; false only for a category the specs mark as a service). Check constraints in the database for each rule, and the same rules in the contract.
2. **Serial pattern:** a JavaScript regular expression source, compiled with `new RegExp(source, 'u')` and anchored by the code (`^(?:…)$`); refused when it does not compile, when it matches the empty string, or when it is longer than 200 characters. Export `serialMatchesPattern(item, serial)` from `packages/domain/src/catalogue/` for U2 and H3 to use. No serials table exists yet (H1 adds it), so the check against existing serials is a TODO for H1's merge: write it as a function that takes the serial list and leave its caller to H1, saying so in your report.
3. **Specifications:** check `packages/contracts/src/catalogue/specs.ts` for `structure`, `cable`, `pipe`, `inverter` and `battery`; add the fields an Inventory Manager needs to tell two items apart (for example a cable's cores, size in mm² and conductor; a pipe's diameter, class and length per piece; an inverter's kVA and phase; a battery's Ah and voltage), each optional, with units in the key names as C1 did.
4. **Commands:** `catalogue.item.create` and `.update` take the new fields (All companies only, as now) and audit them; no new command.
5. **Import:** a new kind `items` in the imports framework (P2b): the columns the design lists; an unknown category, an HSN not of 4, 6 or 8 digits, a unit outside the list, a bad pattern or a duplicate barcode refuses the row with its reason in the row report; a known SKU updates the item through `catalogue.item.update`; only from All companies (`catalogue_needs_all_companies`). Measure a 5,000-row import on the local stack and record it in your report.
6. **Screens:** the item sheet's Stock and warranty section (read for every reader of the catalogue, edited with `catalogue.write` from All companies); Import items beside the items grid; plain English in `en.json`, button labels within 24 characters.

Files owned: `packages/db/src/schema/items.ts` and its migration, `packages/contracts/src/catalogue/`, `packages/domain/src/commands/catalogue/items.ts`, `packages/domain/src/catalogue/` (new helpers), `packages/domain/src/queries/catalogue/`, the items import kind, the item sheet and grid under `apps/web/src/app/(bos)/catalogue/`.

Do not touch: anything of `inventory`, `procurement`, `warehouses`, `bins`, `stock_*`, `serials` or `vendors` (H1 and U1 own them); `kits` and `pump_curves` beyond reading.

Review checklist (check before your report): every new rule holds in the database as well as the contract; an Inventory Manager in one company cannot change an item; the import refuses each bad row with its reason and never half-writes an item; `docs/data` regenerated; the item sheet's snapshots in light, dark and 400 px.

**Assumptions** (calls the brief left open)
1. **Services:** no category is a service today, so `NON_STOCK_CATEGORIES = ['other']`: only an Other item without serials may be left out of stock (`items_stocked_check`, the form shows the box for Other only). A `service` category would widen the category list and every screen of it; the lead or owner can choose that instead.
2. **Factor rules:** a factor only with a purchase unit; required when that unit differs from the stock unit; null or 1 when it is the same.
3. **Barcode:** printable ASCII without spaces (`[!-~]{4,64}`), compared exactly; declared a long number by design in `unmaskedFields`, as `sku` is.
4. **Serial pattern safety:** besides the brief's three refusals, a repeat around a repeating group (`(a+)+`) is refused (`nested_repeat`), since a pattern is run on every scan; and a serial longer than 100 characters never matches. Both are mine.
5. **Early check:** the agent file asks a Tier B builder to stop after the schema and commands; the run file lists only `done`, `fixes` and `blocked`, so I built through without stopping. The commits are layered (schema, commands, import, screens) for the lead to read in order.
6. **Specifications:** existing required keys stay required (sizing reads them); the new keys are optional, the form leaving a blank one out.
7. **Who imports items:** `imports.write` and `catalogue.write` from All companies, that is the Executive and the General Manager; the Inventory Manager holds `catalogue.write` but not `imports.write` and is not offered Import items. Giving them `imports.write` is a matrix change for the owner.
8. **Import columns:** the design's list plus the serial pattern (the brief names "a bad pattern" as a refusal). The code is the only required column. A blank cell keeps what an item has, so a file cannot clear a value. The stocked flag is not a column. A new item of a category with required specifications (pump, motor, solar module, controller, pipe, inverter) is refused with `item_details_needed`, since the file carries no specifications; changing such an item from a file works.
9. **Commit and rollback:** each row runs `catalogue.item.create` or `.update` as the importer, with its own audit row and event; a row the catalogue no longer takes at commit (barcode taken since, item archived since, the merged row no longer valid) is set aside with its reason, and its savepoint leaves nothing. The rollback archives the items the file added in one statement a chunk under a lock, keeping any a kit still sold holds; changes stay, their before and after in the Activity log. I first ran `catalogue.item.archive` per item, but that writes an audit row per item in one insert, which broke Postgres's parameter limit at 5,000 items. So the rollback is set-based like the leads rollback, the job's own audit row counting what it archived and kept, and it emits no `catalogue.item.archived` per item.
10. **Hidden barcodes:** a twelve-digit barcode whose check digit is an Aadhaar number's is hidden by the file reader before the preview; such a row is refused with `barcode_hidden`, so a masked value is never stored as a barcode.
11. Shared files touched, one block each: `en.json`, the import kinds' registry (`imports/enums.ts`), `contract-values.ts` (the `items` kind; the specification values moved out), `enum-sync.test.ts`, the event catalogue's `emittedBy`, `copy-lint.config.json`.
