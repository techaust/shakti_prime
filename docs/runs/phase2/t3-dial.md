**Decisions the brief did not settle**
1. The provider is asked after `calls.call.dial` commits, not inside its transaction: no call is placed for a dial that rolled back, and no transaction waits on Exotel's 8 s. The platform records the provider's id (`calls.process`), so after the insert no person writes anything but the log link.
2. `placeDial` checks the plan first (with E1's DND refresh and the accurate `dnd_not_set_up`) and throws `dial_refused` without running the command; such a refusal writes no audit row. The command checks again in its own transaction on the recorded DND state (a stale promotional check is `dnd_unknown` there), which is the guarantee.
3. A dial takes no idempotency key (its answer carries the phones, which a stored answer would keep); a second press within 60 s while the caller's last call is dialling or ringing is refused (`dial_in_progress`).
4. A provider timeout leaves the call `dialling` without an id, never placed again; the signed status report adopts the CallSid when the call has none (the reference is ours, signed), and never a CallSid another call holds.
5. No state machine for the provider status: it is the provider's report, written only by definers, kept forward-only by the database trigger (`machines:docs` unchanged).
6. `calls.recording.play` is a command (so each listen is audited) answering the stored location to the server only; the 15-minute address is signed by the action (step 6) with `PRESIGN_SECONDS`.
7. Listening scope is the lead's owner and team (`app.scope_ok('calls.recording.listen', …)`), as the call is read with the lead.
8. The recording file is written by the definer (`ready`, `scan_result` `{scanner: none, source: call_provider}`), content type MP3 or WAV, key `<company>/call_recording/<file id>.<ext>`; `UploadContentType` is left alone (K3 may add audio there).
9. The dial phone is per company (`caller_profiles` is), under `calls.dial:own`; `CallerProfileDto` does not carry it.
10. A dialled call's log keeps the provider's length when reported, else the screen's.
11. `provider_calls.opportunity_id` is required, as the brief's columns and the read rule need; T4 may relax it for an inbound call with no customer.

1. Exotel cannot play the notice on a click-to-dial call as the client is built: `Calls/connect.json` connects two numbers with no flow before the caller is joined. Exotel can connect a number to a flow instead, but that flow would need a dynamic Connect applet asking the BOS which customer to ring, which is not built. Calls are therefore placed unrecorded (the adapter sends `Record=false`), as the brief says, and the notice is the first line of the call bar ("Say this first:"), in the customer's language. The notice's wording says the call "may be recorded", true either way. A one-line change in the adapter turns recording on once a flow plays the notice.
2. The notice sits on the call bar, not the script card: Converting has no script card, and the bar is where the call is placed in both workspaces.
3. `C` dials in the Cold Caller workspace only: in Converting `C` is already the callback key (Phase 1), so the bar there has the button without a key. The lead may pick another key for Converting.
4. Unplaced dials are closed by the hourly files sweep, not a new nightly schedule: no new QStash schedule or hosted step is needed, and a timeline is right within two hours.
5. A recording's file id is the provider call's id, so a retried delivery puts the same key and the attach answers `already`; no orphaned bytes.
6. The simulated provider stands in on every runtime that is not hosted and has no Exotel account (as E1's fixture DND register does), so a developer and the journeys can dial; a hosted runtime without the account offers no Call.
7. `dialReadiness` carries the notice text to the browser, since browser code takes only types from the contracts.
8. Recording hosts are Exotel's own and its S3 bucket in Singapore or Mumbai; the spike's step 5 confirms them on the live account.
