**`app_backup`, weighed**
- *The login.* `bypassrls` with `select` on the six schemas, no definer and no membership is the narrowest role that gives a complete logical copy. The alternatives are worse:
  - `pg_read_all_data` reaches every schema, Supabase's own included.
  - A login without `bypassrls` needs its own `using (true)` policy on every table and partition, kept right by hand, and pg_dump stops at the first table one leaves out.
  - A session that sets every company and permission still misses the rows only definers reach.
- *The password.* It lives in two GitHub environments and the owner's store. In `production` it waits for approval; in `production-backup` it does not, which is H2.
- *The recommendation.*
  - Keep the login as built and fix H2: the token change at least, and the dump run in AWS if the lead is to keep editing workflows.
  - Name Supabase Pro's daily backups as the second way back (M5).

## Integration notes
- The pull request changes `.github/`, `turbo.json` and adds workflows, so it merges only after the owner adds `checks-ok` (DECISIONS, 13-10-2026).
- Nothing is applied to production by the merge: the first release is a separate, approved run.
- **Before the merge** (H1, L2, L12): the owner's steps of DEPLOY §1 step 4 a to c (delete `Production`, create `production`, the lead's read-back), since from the merge on anyone with write access can start `release.yml`; the lead reads `production` back again just before the merge. The secrets (d), the lead's narrower token (e) and the ruleset (f) may follow. There is no `production-backup` environment and no backup workflow: the backup stack (§1 step 9) is made in AWS whenever the owner chooses before the first release, and the backup login's password straight after it.
- The migration `*_backup_role.sql` (grants to `app_backup`) moves after `main`'s last at the merge; no test or code cites its number (`release-workflows.test.ts` finds it by its name). It redefines no function, check or foreign key.
- **The proof of the release gate (L2)**, on GitHub before the merge, never touching production. `workflow_dispatch` starts only a workflow on the default branch, so the proof is push-triggered:
  1. The owner makes the environment `release-proof`: *Required reviewers* the owner, *Deployment branches and tags* the one branch `proof/release-gate`, no secrets.
  2. The lead pushes the branch `proof/release-gate` (from this branch) with one extra file, `.github/workflows/release-proof.yml`: a copy of `release.yml` started `on: push` for the branches `proof/release-gate` and `proof/release-gate-other`, whose `check` job keeps only *Only from main* with the ref it accepts changed to `refs/heads/proof/release-gate`, whose `release` job names `environment: release-proof` and `if:` that ref, and whose every step after the environment is replaced by an `echo` (no migration, tag, hook or address of any site).
  3. The run on `proof/release-gate` passes the check and waits at *Review deployments*; the owner **rejects** it. The lead records the run's address and its *Waiting* and *Rejected* states.
  4. The lead pushes the same commit as `proof/release-gate-other`: its `check` job stops at *Only from main* (the plain message). Then a second commit on that branch that removes the guard and the `if:` (a branch's own copy dropping the checks): the `release` job is refused by the environment's branch rule (*Branch "proof/release-gate-other" is not allowed to deploy to release-proof due to environment protection rules*). The lead records both runs.
  5. The owner deletes the environment `release-proof`. The two proof branches stay on GitHub (no remote branch is deleted, CLAUDE.md); their names say what they are.
