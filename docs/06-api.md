## 1. Conventions
| Concern | Rule |
|---|---|
| Base URL | `https://shaktiprime.com/api/v1` |
| Versioning | Path version. Breaking changes ship as `/api/v2` with `/api/v1` supported for 6 months; the field app's minimum-version gate enforces upgrades |
| Contracts | Every request and response schema lives in `packages/contracts` as Zod; route handlers parse with them and never hand-roll validation |
| Content type | `application/json; charset=utf-8`; file bytes never pass through the API (pre-signed S3 URLs) |
| IDs | UUIDv7 strings |
| Time | ISO 8601 UTC in payloads; the client renders IST |
| Money | Strings with two decimals (`"12345.50"`) to avoid float drift; currency always INR |
| Idempotency | `Idempotency-Key` header (UUID) required on every mutating call from the field app and the connector; keys are stored in `idempotency_keys` for 7 days (Redis in front from the mobile API onwards) and replay the original response; a repeat with a different body answers `conflict` (reason `idempotency_mismatch`); a call that failed stores no key, so its retry runs again |
| Pagination | Cursor: `?cursor=<opaque>&limit=<1..200>`; responses carry `nextCursor` |
| Rate limits | Per token via Upstash Redis, with the bearer tokens (Phase 4); the built routes keep their own caps, named in their rows; `429` with `Retry-After`; defaults 600 req/min per user token, 60 req/min per ingest key |
| Errors | One envelope: `{ "error": { "code": "forbidden", "message": "…", "details": {...}, "requestId": "…" } }`; codes from `packages/contracts/src/errors.ts` |
| Request ID | One rule for every route, server action, auth event and error log line (`apps/web/src/request-id.ts`): Vercel's `x-vercel-id` when present (a new id when it is not safe to echo), else the caller's `X-Request-Id` when it matches `[\w.:-]{1,128}` (QStash, a monitor, a local run), else a new id, so on a hosted deployment a caller cannot choose the id an audit row or a log line carries; echoed in the response and the logs |
| Localisation | Messages in error envelopes are English; `Accept-Language` is not negotiated |

### Error codes
`validation_failed` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `conflict` (409, state machine or idempotency conflict), `rate_limited` (429), `integration_unavailable` (503), `internal` (500).

## 2. Authentication
| Caller | Mechanism |
|---|---|
| Web app (server actions, built) | Better Auth session cookie (HttpOnly, Secure, SameSite=Lax) with CSRF origin checks; TOTP step-up for Executive, GM, Accounts |
| Field app (Phase 4) | `POST /auth/mobile/token` exchanges credentials (+ TOTP where required) for a 15-minute access token and a refresh token bound to the device; refresh tokens rotate; per-device revocation |
| Voice agent (Phase 2) | The BOS mints a 5-minute user-scoped token when a voice session starts; the worker sends it as `Authorization: Bearer` so every command runs as the speaking user |
| Tally connector (Phase 5) | Per-connector key; every request carries `X-Connector-Id`, `X-Timestamp` and `X-Signature` (HMAC-SHA256 over method, path, timestamp and body); 5-minute clock skew window |
| Website ingest (Phase 2) | Per-entity ingest key in `X-Ingest-Key` plus a Cloudflare Turnstile token in the body |
| Provider webhooks (Phase 2) | Provider signature verification before any processing: Meta `X-Hub-Signature-256`, the Google Lead Form key, and for Exotel, which sends no signature header, a StatusCallback address per call that carries the BOS call id, an expiry and an HMAC-SHA256 of both under `EXOTEL_CALLBACK_SECRET` (`apps/web/src/integrations/exotel/status-callback.ts`) |
| Workers (built) | QStash signature (`Upstash-Signature`) verified with the current and next signing keys |

Every authenticated call runs inside `withRequestContext()` with the caller's principal and entity scope.

## 3. Endpoint catalogue
Every `/api/v1` route below except seven is an entry of `API_ENDPOINTS` in `packages/contracts/src/api/endpoints.ts`, which names its request, query and response schemas and its error codes; schema files are under `packages/contracts/src/api/`. The seven exceptions are the signed schedule targets of §3.6, `/workers/files/sweep`, `/workers/crm/rescore`, `/workers/crm/duplicates`, `/workers/quotes/expire`, `/workers/notifications/scan`, `/workers/jobs/check` and `/workers/crm/anonymise`, which sit outside the catalogue and have their bodies and answers in `workers.ts`. `packages/contracts/src/api/fixtures.ts` holds a recorded example for each route, and `endpoints.test.ts` fails when a route here and the catalogue differ (the seven exceptions are not compared). Every authenticated route can also answer `rate_limited` (429 with `Retry-After`) and `internal`; the Errors column lists the rest, with `details.reason` where the caller acts on it.

A row marked **(built)** is served today; every other row is the contract for the phase that builds it, named under each heading. The routes outside `/api/v1` are in §3.8 and §3.9.

### 3.2a Uploads
The two calls of an upload ([ARCHITECTURE §9](04-architecture.md#9-files-masking-and-print)): the screens reach the same commands through the server actions in `apps/web/src/actions/files.ts`, and the field app through these routes from Phase 4. File bytes never pass through the API.

| Method | Path | Auth | Purpose | Contract | Response | Errors |
|---|---|---|---|---|---|---|
| POST | `/files/presign` | session (bearer with the mobile API, Phase 4) | (built) Records an upload (`files.upload.begin`) and answers a 15-minute pre-signed PUT with the type, length, SHA-256 and encryption bound into the signature; at most 60 calls in five minutes per person | `files.ts`: `FilePresignRequest` (`entityId`, `purpose`, `name`, `contentType`, `size` ≤ 15 MB and the purpose's limit, `sha256`); `Idempotency-Key` | `FilePresignResponse`: `{ fileId, method: PUT, uploadUrl, headers, expiresAt }` | `validation_failed` (`file_type_not_allowed`, `file_too_large`); `unauthorized`; `forbidden`; `rate_limited`; `conflict` (`idempotency_mismatch`); `integration_unavailable` (`files_unavailable`) |
| POST | `/files/:id/complete` | session (bearer with the mobile API, Phase 4) | (built) The bytes landed: the store's size and SHA-256 must be the declared ones (`files.upload.complete`); the file waits for its checks and is usable once a later read shows `ready` | `FileCompleteParams`, `FileCompleteRequest` (`purpose`); `Idempotency-Key` | `FileCompleteResponse`: `{ fileId, status: scanning }` | `validation_failed`; `unauthorized`; `forbidden`; `rate_limited`; `not_found` (`file_missing`); `conflict` (`file_upload_mismatch`); `integration_unavailable` |

An import file (purpose `import`: a CSV or an `.xlsx` workbook, at most 10 MB) takes the same two calls, as every file does; no file reaches a server action as a form, so the server actions keep Next.js's default body limit. Once its checks leave it `ready` (its bytes are the format its type declares, and a workbook's archive is one the reader may open), the import screen's action `startImport` reads it back from the store, a workbook through ExcelJS's streaming reader, and starts the job (`imports.job.create`); a file still in its checks answers `import_file_not_ready`, and a file of the same content as one whose job is adding or has added its rows in the company `import_file_duplicate`, at the start and again when its job commits. An upload still `pending` a day after it began is cleared by the hourly sweep (§3.6).

On a developer's machine, where no S3 bucket exists, the signed address is `PUT /api/v1/files/local/<token>` on the app itself (and `GET` for a download): the token is the store's signed grant for one key, type, length and SHA-256, and every hosted deployment answers 404 there. It is not part of the contract catalogue.

### 3.3 Ingest (entity websites, partners)
Phase 2, with the website forms (PRD CRM-01). Built (I1, [phase 2 design §6.2](03-roadmap-appendix/phase2.md#62-i1-lead-ads-lead-forms-and-website-ingest)) in `apps/web/src/ingest/routes.ts`. Before anything is written, in order: the key in `X-Ingest-Key` found by its SHA-256 (`unauthorized`, reason `ingest_key_refused`, for an unknown or turned-off key), 60 a minute per key (`rate_limited` with `Retry-After`), a body of at most 16 KiB that reads as the contract (`validation_failed`), the key's company named as `entityCode` (`forbidden`, `ingest_key_other_company`), and Turnstile (`forbidden`, `turnstile_failed`; `integration_unavailable` when Cloudflare cannot be asked). The lead is then made in the request as the platform (`crm.lead.ingest`, channel `website`). Each key may be tied to one of its company's connected websites when it is made (`ingest_keys.source_id`): that site gives the lead's line of business (unless `segment` names one) and what its consent box agrees to; the site is taken from the key, never from the request. A consent is recorded only when `consent.ticked` is true and the key's site has a consent setting, with that setting's channels and purpose (a `purpose` the request sends is ignored) and the SHA-256 of the wording sent as its version. A key with no site needs `segment` (`validation_failed`, `lead_source_missing`) and records no consent. An empty `message` counts as none. An `Idempotency-Key` makes a retry act once. Without a Turnstile secret both routes answer `integration_unavailable`.

|---|---|---|---|---|---|
| POST | `/ingest/leads` | `{ entityCode, name, phone, pin?, segment?, message?, utm?, consent?: { ticked, purpose?, text, givenAt }, turnstileToken }` → lead created or attached; returns `leadId` | `ingest.ts`: `IngestLeadRequest` (phone normalised to E.164 on parse) | `IngestLeadResponse`: `{ leadId, outcome: created \| attached }` | `validation_failed` (`lead_source_missing`); `unauthorized` (`ingest_key_refused`); `forbidden` (`turnstile_failed`, `ingest_key_other_company`); `rate_limited`; `integration_unavailable` |

### 3.4 Provider webhooks
Phase 2. Every route is built (P5, [phase 2 design §5.1](03-roadmap-appendix/phase2.md#51-p5-webhook-backbone)) through one helper, `receiveWebhook()` in `apps/web/src/webhooks`: it stores each delivery that passes its check and processes it with its provider's handler, or marks the row `no_handler` while the slice named in its row has registered none (Exotel's call status has T3's; Lead Ads and Google lead forms have I1's). Provider payloads are loose schemas: unknown keys are kept, and only the fields the workers act on are required, so a field a provider adds never fails parsing while a changed field the BOS relies on does. Each delivery answers `WebhookAck` (`{ received: true }`) within 2 seconds once the payload is stored (a repeat of a stored provider event gets the same answer and is processed no more); `validation_failed` for a body over the cap (256 KiB for Meta, 64 KiB for the rest), before anything else is read; `unauthorized` when the signature or key check fails, counted per provider and hour and never stored; and `integration_unavailable` while the route's secret or `DATABASE_URL_WEBHOOKS` is not set (production until the final phase) or the delivery could not be stored, so the provider sends it again.

### 3.5 Tally connector
Phase 5 (ADR 0013). Contracts in `connector.ts`; routes in `apps/web/src/integrations/tally/routes.ts` (built, TC2). Every call carries `ConnectorHeaders`; the signature is HMAC-SHA256, as lowercase hex, under the connector's key as it was shown once (or, during a rotation, its next key), over `connectorSigningString()` (method, the path with query exactly as it arrived with a space as `+`, Unix-seconds timestamp and the body's SHA-256, one per line), and a timestamp outside `CONNECTOR_CLOCK_SKEW_SECONDS` (300) answers `unauthorized`, as do an unknown or revoked connector and a wrong signature (reason `tally_connector_refused`). The headers and the timestamp are checked before the body is read or the database asked, and a connector id and an address each make at most `TALLY_CAPS` calls a minute (240 and 600; beyond, `rate_limited` with `Retry-After`). The BOS keeps each key only sealed by the field cipher (KMS on a hosted environment) and opens it to check a call, keeping what it read of a connector for a minute so a call verifies before any transaction (SECURITY §3.3); a runtime with no cipher answers `integration_unavailable`. After the signature and the contract, the call runs as the connector's own principal (`system:tally_connector`, DATABASE §6.7) in the one company its Tally company name is mapped to; a body over a function's 4.5 MB answers `validation_failed` (`tally_body_too_large`).

### 3.6 Workers (QStash only)
How events are leased, retried, dead-lettered and held back by the failure callback is ARCHITECTURE §6; every event type, its payload and whether a worker handles it is [events.md](data/events.md). Rules for every worker route:
- **Body cap first:** a body over the route's cap is refused with `400 validation_failed` and QStash's no-retry header before the signature is checked; the caps are in [ARCHITECTURE §6](04-architecture.md#6-events-and-workers).
- **Signature:** the QStash signature (`Upstash-Signature`) is verified with the current and next signing keys.
- **Principal:** the worker runs its command as its principal (a named agent principal or `system:workers`, never with a cost permission) and returns `200` on success or a retryable `5xx`.
- **Duplicates:** an event worker answers `duplicate` without running when it has handled the body's `eventId`, and a delivery that arrives while another holds the id answers a retryable `409 conflict` (reason `event_in_progress`); the claim and the ordering rules are in [ARCHITECTURE §6](04-architecture.md#6-events-and-workers).
- **Bodies** carry ids, codes and counts only. Contracts are in `worker-jobs.ts` unless the row says otherwise; each answer is `{ eventId, outcome: duplicate }` or `{ eventId, outcome: done, … }` with the fields listed.
- **Errors for every worker:** `unauthorized` (signature), `validation_failed` (body, not retried), `integration_unavailable` (retried); a scheduled route's third failed call in a row (`500`, or `503` for a lock it could not get) tells the owner (`job.failing`, DEPLOY §1 step 8); the import commit worker also answers `403 forbidden` with the no-retry header when the person who asked is suspended or has lost the import permission in that company.

## 4. Server actions (web)
- Live in `apps/web/src/actions/<module>.ts`, one exported function per command or query, each a thin wrapper: resolve the caller from the session → `parseInput()` with the contract → `executeCommand()` or `executeQuery()` (which open `withRequestContext()`) → answer the `ActionResult` envelope (`apps/web/src/actions/result.ts`): `{ ok: true, data }` with the DTO, or `{ ok: false, error, field?, reference? }` naming a catalogue sentence, because Next.js masks errors thrown from a server action in production. The Better Auth actions in `actions/auth.ts` answer a `{ error }` form state instead.
- No business logic in actions. No direct database access in components.
- Reads for pages use typed query functions in `packages/domain/src/queries`, called through `executeQuery()`.

## 6. Messaging contracts (outbound WhatsApp)
Commands never call Meta directly. A command queues the message in `whatsapp_messages` (status `queued`, its text or template values masked) and emits the catalogue event `messaging.message.requested` with `{ messageId, threadId, kind }` (`MessageRequested` in `packages/contracts/src/api/messaging.ts`: ids and the kind only, as every event): `messaging.message.send` (a person's text in the window or approved template), `messaging.message.queue` (the platform's welcome, or the confirmation of a STOP), `messaging.milestone.send` (a customer update's template, once per subject) and `messaging.answer.queue` (the platform's own answers: STATUS, an acceptance, a code that does not match, the one-time code, a quote no longer open). The event goes to `/workers/messaging/send` as a `MessagingSendJob`, or is handled in process where no queue is set up.

WhatsApp quotes ([phase 2 design §7.1](03-roadmap-appendix/phase2.md#71-s3-whatsapp-quotes-milestones-and-status)) have no route of their own: they are event workers on `/workers/outbox/:type`. `sales.quote.sent` with the channel `whatsapp` sends the `quote_sent` milestone, telling the event's `sentBy` (`whatsapp_quote_not_sent`, through `notifications.event.notify` in the same run) when it is not queued, and `sales.order.confirmed` the `order_confirmed` one (`apps/web/src/workers/messaging/milestones.ts`); `messaging.button.pressed` answers a quote's Accept and Talk to us buttons (`quote-press.ts`). As it sends, the messaging worker makes what is never stored: a quote's two button payloads (`q1.<a|t>.<quote>.<HMAC>` under `WHATSAPP_BUTTON_SECRET`, bound to the quote, the chat and its number, `packages/domain/src/messaging/quote-button.ts`), the quote's PDF as the template's header document (a short-lived signed address), and an authentication template's six-digit code (from the message's id under the same secret, in its body and its copy-code button, `acceptance-code.ts`). A template maps to a milestone only with the header and buttons the worker sends with it (`WHATSAPP_MILESTONE_SHAPES`), and the code's template is an authentication one with one copy-code button (`WHATSAPP_PURPOSE_SHAPES`), since Meta refuses a message whose parts differ from its template. The WhatsApp handler answers STATUS and a code itself (six digits only while a code is valid on the chat) and marks their `messaging.message.received` with `platform: true`; `isHandledByPlatform()` (`apps/web/src/workers/messaging/handled-by-platform.ts`) reads the mark.

The WhatsApp Concierge ([phase 2 design §7.2](03-roadmap-appendix/phase2.md#72-a3-whatsapp-concierge)) has no route of its own either: it is the event worker of `messaging.message.received` on `/workers/outbox/:type` (`apps/web/src/workers/concierge/concierge-event.ts`), which leaves a message the platform answers alone and records the assistant's drafts; a person sends a draft through the Agent Inbox's decisions (`agents.inbox.approve`, `.edit`, `.reject`).

The messaging worker (`apps/web/src/workers/messaging/send.ts`, `decideSend` in `packages/domain/src/messaging`) enforces, in order: opt-out (but the one STOP confirmation), the 24-hour window for free text, the template's approval, the portfolio budget (business-initiated chats to distinct customers in a rolling 24 hours against the limit Meta reports, marketing templates held at `WORKSHOP_DEFAULTS.whatsapp.marketingHoldShare`), the deterministic output filter and `WORKSHOP_DEFAULTS.whatsapp.messagesPerThreadHour` per thread; then it takes the message once (`messaging.message.claim`), sends it with the company number's client and records `provider_message_id` (`messaging.message.record_send`). Statuses from the `meta_whatsapp` webhook move `whatsapp_messages.status` only forward (`messaging.status.record`).

## 7. Compatibility and deprecation
- Additive changes (new optional fields, new endpoints) ship without a version bump.
- Removing or changing a field requires `/api/v2` and a deprecation notice in the `Deprecation` and `Sunset` headers on `/api/v1` responses for 6 months.
- Contract tests with recorded payloads for Meta, Exotel, Google and Tally run in CI; a provider payload change that breaks parsing fails the build, not production.
