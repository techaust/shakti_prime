# Verdict on auditor 3 (domain correctness), main at 23f78a5

## How the findings were checked

Each command-level claim was run with the real domain commands (`runCommand` with the database audit and outbox sinks) as `app_user`. Everything ran inside **one transaction per script, rolled back at the end**. Afterwards there were 0 `verify` principals, 0 `sales_orders` and 0 `quotes`, so nothing persisted.

How the harness works:
- **Fixtures.** `postgres` cannot `SET ROLE app_user`: it is a member with ADMIN but not SET. So the harness connects as `app_user`, and writes the fixtures (principals, team, tier, items, price list, tax rates, files, a dealer, a second lead, synthetic committed import jobs) under a context holding every permission. No DDL was run, and no trigger was disabled.
- **Each command** then runs in its own savepoint, with exactly the `set_config` calls that `withRequestContext()` makes for its principal. The roles are the seeded grants (`principalFor`): `tele_caller_lc` (the Lead Converter), `sales_team_lead`, `general_manager`, `accounts`, `executive`, and `system:workers` for the PDF.
- **Scripts:** `scratchpad/verify/harness.mts`, `fixtures.mts`, `dom1.mts`, `dom2.mts`, `dom3.mts`, `dom4.mts` and `dom5.mts`. Run from `packages/domain` with the repo's `tsx`.
